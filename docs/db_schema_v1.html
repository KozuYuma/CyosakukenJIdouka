Database Schema Design

著作権調査支援ツール
DBスキーマ設計

NUENDOのCueシート照合から権利情報確定まで、調査ワークフロー全体を管理するためのテーブル構成です。

テーブル関係の概観
projects 1 ──< songs >── N nuendo_events
songs 1 ──< rights_search_results  /  wav_files  /  mp3_files
songs が中核テーブル。wav_files・mp3_files は照合ソースデータ、rights_search_results は検索キャッシュ兼候補履歴として独立します。master_db_entries と import_logs はプロジェクト横断で使用します。
projects プロジェクト
性質: 案件・番組・映像作品単位の親レコード。1回の納品ワークフローを1プロジェクトとして管理する。変更頻度は低く、他テーブルのスコープ境界として機能する。
カラム名型・制約説明
idPKINTEGER自動採番
nameTEXTNOT NULL案件名（例: ◯◯劇場版 BGM調査）
descriptionTEXT補足メモ、放送日、依頼元など
created_atTIMESTAMPプロジェクト作成日時
updated_atTIMESTAMP最終更新日時
songs 楽曲まとめ
性質: 本ツールの中核テーブル。NUENDOイベント名単位でユニーク化した楽曲情報をすべて集約する。照合結果・手動入力・自動検索の書き込みが混在するため、更新頻度が最も高い可変データ。確認ステータスの遷移が調査進捗を表す。1プロジェクトあたり数十〜数百件。

updated_atTIMESTAMP最終更新日時（ステータス変更・権利情報入力のたびに更新）
nuendo_events NUENDOイベント一覧
性質: Cue CSVをそのまま格納するappend-onlyに近い生データテーブル。同一楽曲が複数トラックで複数回使用される場合に複数行となる（songs とは N:1 の関係）。照合実行後に上書きインポートされる。1プロジェクトあたり数十〜数千件。
カラム名型・制約説明

project_idFKINTEGER所属プロジェクト

usage_durationTEXT使用尺（Cueシート記載値）
wav_match_statusENUMWAV照合ステータス（songs と同値・非正規化コピー）
wav_files WAVファイル一覧
性質: フォルダスキャンまたはCSVから取り込むファイルシステムのスナップショット。再スキャンで上書き。照合の参照元として使われるが、照合後は songs.wav_matched_filename に結果が移る。変更頻度低。数百〜数千件。
カラム名型・制約説明
idPKINTEGER自動採番
project_idFKINTEGER所属プロジェクト
filenameTEXTファイル名（拡張子含む）

durationTEXT再生時間（HH:MM:SS.mmm）
scanned_atTIMESTAMPスキャン or インポート日時
mp3_files MP3ファイル一覧（mp3finder出力）
性質: nuendo_mp3_finder.py の出力CSVを格納するID3タグ付き照合結果テーブル。イベント名と照合種別を持ち、作曲者・アーティスト情報の主要ソース。1イベント名に対して複数行（マッチ種別違い）があり得る。WAV非依存で使える貴重な情報源。
カラム名型・制約説明
idPKINTEGER自動採番
project_idFKINTEGER所属プロジェクト

filenameTEXTマッチしたMP3ファイル名
durationTEXT再生時間
id3_titleTEXTID3タグ: タイトル
id3_artistTEXTID3タグ: アーティスト
id3_albumTEXTID3タグ: アルバム（CD品番の手がかり）
id3_composerTEXTID3タグ: 作曲者（J-WID検索のヒントとして最重要）
rights_search_results 権利情報検索結果
性質: J-WID・NexTone・MusicBrainz・Spotifyの検索結果を候補履歴＋キャッシュとして保存するテーブル。1曲あたり複数候補が存在し、applied フラグで適用済みを管理する。同一曲を再検索した際の差分確認にも使える。時間経過で情報が古くなるため、searched_at での鮮度管理が重要。

song_idFKINTEGER対象楽曲
sourceENUMJASRAC / NexTone / MusicBrainz / Spotify / Claude
search_termTEXT使用した検索語

searched_atTIMESTAMP検索実行日時（キャッシュ鮮度の判定に使用）
master_db_entries マスターDB
性質: Accessや社内DBからエクスポートした社内確認済み権利情報の静的マスター。songs への補完ソースとして使われ、更新頻度は低い。プロジェクト横断で参照され、数千〜数万件になり得る。自動検索で拾いにくい古い曲・ライブラリ音楽の情報源として特に有効。

import_logs インポート履歴
性質: CSVやExcelの読み込み操作を記録する監査ログ。"どのファイルをいつ読み込んで何件処理したか"を追跡するための append-only テーブル。デバッグや再現性の確保に役立つ。
